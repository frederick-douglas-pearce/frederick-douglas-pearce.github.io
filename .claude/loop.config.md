# Loop config — frederick-douglas-pearce.github.io

Per-project bindings for the supervised dev loop. `loop-engine.md` (the generic engine, bundled in
the plugin) references every value below **by parameter name**; this file is the only surface a
porting project edits. A non-matching (non-Python / non-`src/` / non-GitHub) project revises **all
four sections** (parameters, architect triggers, source layout, security routing) — never the
engine.

See `${CLAUDE_PLUGIN_ROOT}/skills/dev-loop/loop-engine.md` for the operating procedure and semantics.

> ⚠ **Generated by `/init-loop` — review before the first run.** Values are best-effort inferences;
> every `TODO(init-loop)` is a blank you must fill (or delete if it does not apply to this repo).
> Hand-tuned on 2026-10-26 from the onboarding notes in #112.

This repo is a Jekyll fork of the al-folio theme (Liquid, SCSS, kramdown, a few Node scripts in
`bin/`). It has **no test suite**. Verification is Prettier, a successful Docker build, and, for
anything that changes rendered output, `VERIFY`'s screenshot and accessibility audit. Read
`CLAUDE.md` before planning any issue: most of what makes a change here go wrong is recorded there,
and the header comments in `_includes/*.liquid`, workflows and `_config.yml` blocks record several
decisions _not_ to do the obvious thing.

## 2. `ARCHITECT_TRIGGERS`

**These triggers govern the plan-informing use only, and the list below does not bound
`DESIGN_AGENT`.** The engine consults that agent for a scope ruling whenever a BLOCKING
code-review finding raises a design question — on every route, and stopping with that ruling.
Nothing in this file turns that off.

Fire `DESIGN_AGENT` when the plan does any of the following, or when the orchestrator is unsure.
Bias toward calling it. Skip for the `docs` route.

- Adds or changes a workflow under `.github/workflows/`, or anything on the deploy path:
  `deploy.yml`'s timeouts, retry ladder or `pages` concurrency group (tuned for the ~14:01 UTC ESG
  feed SLA; see the comments in `deploy.yml`), or a workflow that commits to the repo.
- Adds a `_plugins/` plugin, a build-time network dependency, or a third-party library to
  `_config.yml`.
- Adds a generated or machine-written file under `_data/`, or changes how one is written. It must be
  Prettier-stable or explicitly `.prettierignore`d; `esg_news.json` has broken the check before.
- Changes an include or layout used on more than one page (`header.liquid`, `head.liquid`,
  `activity.liquid`, `_layouts/default.liquid`), or the `_config.yml` keys that shape the build
  (`collections`, top-level `defaults:`, `include`, `exclude`, `jekyll-archives`).
- Touches code whose header comment records a decision _not_ to do the obvious thing (see
  `CLAUDE.md`), or would reverse such a decision.
- Adds a dependency to `package.json` or `Gemfile`. (Ad hoc tooling deps are installed with
  `npm install --no-save` and stay out of `package.json` on purpose.)

When the issue belongs to an epic that has already had a design review (#54 did, on 17 Aug), the
architect checks the plan against the decisions recorded in the epic body, including the options it
lists as rejected, rather than re-opening them.

  `_bibliography/`). Scripts are plain Node CJS in `bin/`. **No tests.** Throwaway scaffolding goes

- **`docs` route:** only changes confined to real prose: `doc/`, `README.md`, `CLAUDE.md`. The
  `documentation` label alone does not make an issue `docs` (#60 carries it and changes code).
  Markdown or Liquid in `_pages/`, `_includes/`, `_layouts/`, and the `.md` files that hold site
  content, render, so they route as `code`. So do `_sass/`, `_plugins/`, `_scripts/`, `_config.yml`

- **`research` label / path:** — (no research label or convention in this repo).
- **`stub-defer` marker:** an epic, an issue titled `Epic: …` (e.g. #54). It is tracking-only and
  never implemented directly: work its children in the order its priority table gives.
- **`code` (default):** everything not routed above → full pipeline.

## 4. Security routing

Run `SECURITY_REVIEW` (local `/security-review`) when the branch touches any of these surfaces,
once the change is dev-complete:

- `.github/workflows/**`: `permissions:`, secrets and tokens, anything that commits or pushes,
  `workflow_dispatch` / `repository_dispatch` wiring, third-party actions and their pins.
- `_plugins/*.rb`: Ruby that runs inside the build, including the code that fetches third-party
  libraries.
- `bin/` scripts that make network calls, read a token or write into `_data/` (e.g. #55's
  repo-stats fetch).
- `_config.yml` entries that add a third-party script, stylesheet or library URL, and `_scripts/` or
  `_includes/` code that loads one (analytics, CDN assets).
- Templates that render externally sourced text into HTML (e.g. GitHub repo descriptions in #56):
  check that it is escaped.

Skip for the `docs` route and for changes with no such surface (SCSS, page copy, layout tweaks).
There is no label-triggered security workflow here; CodeQL runs on every PR on its own.

### ⛔ Precondition — `origin/HEAD` must be set, or the local review gate dies before it runs

**Git-specific, not host-specific** — unlike §4's routing rules above, this needs only git and a
remote named `origin`, and applies on any git host. *You*, reviewing this config, may delete it if
this project does not use git, names its remote something else, or binds `SECURITY_REVIEW` to
something that does not diff against `origin/HEAD`.

`/security-review` opens by diffing against `origin/HEAD`. When that ref does not resolve, the gate
exits with `fatal: ambiguous argument 'origin/HEAD...'` and reviews nothing.

**When it is absent — the rule, not a list of cases.** The ref is set only if the remote's own default
branch was among the refs your clone actually fetched. An ordinary full clone fetches it. It is
**absent** after a `--single-branch` or `--depth` clone of some *other* branch or a tag (the usual CI
checkout), a `--bare`/`--mirror` clone, a `git init` + `git remote add` + `git fetch`, or a clone of a
then-empty repo. It can instead be **dangling** — present but pointing at a branch the upstream has
renamed or deleted — which fails the same way. The check below tests that the ref *resolves*, so it
covers both.

**Repair.** These commands act on **the current directory**, so confirm where you are first — run
from the repo root:

```bash
git rev-parse --show-toplevel
GIT_TERMINAL_PROMPT=0 git remote set-head origin -a
git rev-parse --verify -q refs/remotes/origin/HEAD || echo "still unresolved -- see below"
```

`set-head -a` makes a **network call**: it can hang on an unreachable remote (interrupt it), and
`GIT_TERMINAL_PROMPT=0` suppresses git's own credential prompt but not `ssh`'s. If it reports
`Not a valid ref` or `Cannot determine remote HEAD`, your clone never fetched the remote's default
branch — fetch that branch first, then repeat:

```bash
git fetch origin '<default-branch>:refs/remotes/origin/<default-branch>'
```

**An erroring gate is not a passing gate.** Treat `fatal: ambiguous argument` from this gate as a
missing ref, not as a clean review: repair it and re-run. Never journal it as clean.

## 5. Project examples referenced by the engine's guidance

- **Social copy.** An issue that drafts LinkedIn/X/dev.to/Reddit copy delegates to the user-global
  `marketer` subagent, and the delegation prompt **must name `doc/utm-conventions.md`**: the agent
  carries no UTM values of its own, and a link posted untagged cannot be attributed later.
- **A new blog series** is added to `display_categories` in `_config.yml` _before_ its first post
  syncs (see `CLAUDE.md` "Blog taxonomy").
- **Acceptance without tests (Class B): a rendered-output check stands in for the test.** With no
  test suite, every `code`-route change alters behavior without adding a test, which the acceptance
  gate's mutation pass reports as a Class B finding. So each `code` issue records, in its PR body, a
  cheap check that would fail if the change broke, and the mutation pass mutates against that:
  - a template or style change: a `grep` or HTML assertion against the built `_site/` page (the
    element, class or text the change adds is present; what it removes is gone). For a new class,
    also check that it survives PurgeCSS in the production build (`VERIFY` (a));
  - a script that writes `_data/` (e.g. #55): a shape check on the generated file with an
    independent reader (every curated key present, required fields non-empty, derived values
    compared against their source rather than against the script's own output), plus
    `npx prettier --check` on it unless it is `.prettierignore`d. A shape check sees only the output,
    so the PR body also records the stub failure-path table from `VERIFY` (b);
  - a workflow: `actionlint` where available, plus the specific condition the change relies on.

  The check is a shell one-liner, not new test infrastructure: nothing is added to `package.json`
  and no test runner is introduced. Keep each check fast, because a mutation means a rebuild.
  The Class B "no test added" finding is still raised. The human acknowledges it at the gate, with
  the check as the evidence; it is not waived in advance.
